# Git authentication and code-hosting account audit

Baseline `main` at `10d3165`, after the v2.1.0 release. The source audit and local acceptance use disposable credentials and include an isolated private Gitea server.

| Path | Where authentication is selected | What success proves |
| --- | --- | --- |
| Clone | `CloneSheet` → `AppStore.clone` → `AuthenticationContext.make` → `GitService.clone`. `addRepository` saves the chosen profile before activating a new repository. Opening an existing repository preserves its binding. | The requested Clone completed; public remotes need no credential. |
| Open / rebind | `AppStore.addRepository` validates the canonical working tree and selects an existing record if present. A new record stores the binding before activation. `RepositoryAuthenticationSection` saves a new choice through `AppStore.update`, which invalidates affected Remote Check authentication and requests cancellation for old Fetch targets. | The workspace saved the choice. A transport operation is required to prove that the server accepts it. |
| Fetch / Pull / Push | `RepositoryModel.configure` resolves repository binding, workspace default or system, then supplies Git arguments and process environment to the canonical working-tree `GitService`. `network` uses Git's native targets and helpers. | Git completed that operation. This does not identify which native helper answered. |
| Background and batch Fetch | `WorkspaceModel` reviews a `WorkspaceFetchTarget`, configures the corresponding model, then calls `checkedWorkspaceFetch`. Automatic checks replay native helpers in get-only mode; the GitPier Keychain reader runs without UI. Existing native helpers and configured SSH providers keep their policy. | A completed Fetch verifies access to the reviewed target; `.ready` or a local diagnostic is configuration evidence only. |
| Remote Check | `WorkspaceModel.evaluateRemoteChecks` admits eligible upstream targets to the automatic Fetch coordinator. The observer records the outcome against the current attempt and target. Foreground Fetch records verification only for reconfirmed targets. | A timestamped successful Fetch verifies the corresponding remote. The explicit `ls-remote` probe has its own result and does not record a successful Fetch. |
| Push recovery | `OperationsCenter.verifyPush` configures the model, then `GitService.verifyPush` checks the exact recorded URL/ref. Retry rechecks original configuration, source and target and pushes the fixed object only if needed. | A matching remote reference resolves the specific checkpoint. No unconfirmed result is promoted. |
| Code hosting | `HostingModel` → hosting account/session storage → GitHub, GitLab or Gitea API. OAuth/PAT is scoped to the hosting account and its API instance. | API authorization for that account. It does not establish Git transport access. |

System mode is suitable for users whose existing Git configuration already works. It keeps `credential.helper` (including osxkeychain, Git Credential Manager and GitHub CLI), SSH config, agents, and native transports. No saved GitPier credential is required. Managed HTTPS profiles are useful for explicit account selection: their UUID scopes the Keychain reader, and the helper checks protocol, host and requested username. Managed SSH profiles validate the destination host and select an identity without replacing host-key verification. Binding two same-host repositories to different profile UUIDs keeps credential selection independent; Code Hosting credentials are never substituted into those bindings.

Source inspection identified two cases the settings UI did not distinguish: a workspace default that has never been set, which legitimately uses system authentication, and a saved profile ID whose profile is missing, which must not silently pick a different account. A configured profile is also not evidence that the server accepted it. These distinctions guide the Repository Settings changes and fixture coverage.

Repository Settings now reports the chosen source and the effective profile, including missing or unset defaults, and shows Fetch and Push destinations separately when they differ. **Test Fetch Connection** uses `ls-remote` for a reviewed Fetch target and rechecks its configuration and authentication revision. It does not Fetch refs, write `FETCH_HEAD`, or modify the Index. The result says references were readable; an anonymous success does not prove that a configured token was used, and a readable Fetch endpoint does not prove Push permission. Configured native helpers may still perform their own normal actions when supplying credentials.

The application resolves the profile before starting manual Fetch/Pull/Push or a Push recovery; Commit & Push keeps the local commit if transport configuration cannot be prepared. A missing bound profile fails closed for these paths and for an explicitly selected Clone profile. The unconfigured workspace default still uses system Git. No changes were made to Keychain storage, the provider API token paths, TLS, host-key checks or saved Push verification.

Local evidence in `.cache/v220/phase-c/` includes 73 focused Core cases for same-host profile IDs, existing native Git/SSH and loopback HTTPS, and an actual read-only `ls-remote` with preserved Index, tracking refs and `FETCH_HEAD`. The native foreground fixture used the real Repository Settings button on a local bare remote and verified a missing profile prevents a Fetch. The first run timed out with an off-screen accessory window. The foreground fixture completed with the original assertions. Private hosting instances and production Keychain credentials remain separate acceptance items.

The packaged R3 application also used a loopback OpenSSH server with separate Alpha and Beta keys for two repositories on one host. The server accepted an explicit Alpha binding, rejected the same repository after rebinding to the workspace default Beta key, and accepted that default on Beta's repository. System SSH succeeded with a fixture-native identity and failed without it. A mismatched host key prevented access before upload-pack. The app displayed the failed connection, and the packaged SSH launcher returned the specific host-verification error. The Computer Use run could not expand the Details disclosure. The fixture Git executable appended only a dedicated SSH config to the app's selected SSH invocation.

The connection probes preserved both repositories' HEAD, partial Index, working files, tracking refs and `FETCH_HEAD` status. A subsequent real Fetch advanced Beta's tracking ref, wrote its `FETCH_HEAD` and recorded a successful Remote Check. Both repositories' HEAD, Index and working files still matched their original values. See `.cache/v220/phase-e/ssh-rebind-r3.json`.

An authorized read-only reviewer verified the 334 frozen R3 inputs before and after review. The reviewer found two safety issues. A new Terminal could inherit the previous credential profile while Git work delayed reconfiguration. Retry Push could use an externally amended HEAD after Commit & Push saved a commit and then failed before recording a Push checkpoint. In R5, both Terminal creation paths resolve the current binding and existing sessions retain the environment they started with. A saved commit without a checkpoint requires a matching hash and branch and user confirmation of the validated, redacted current destination. Once a retry has a checkpoint, later attempts retain it even if authentication or preflight fails. Unknown results retain their own original checkpoints.

The separately authorized R5 review closed the remaining R4 findings for Terminal relocation, repeated checkpoint retry and effective Push destination display. All 334 source hashes matched before and after review. Native phases B and C, `workflow210`, `push-recovery` and full Core passed. The review covers seven changed files, with private service testing remaining separate. Evidence is in `.cache/v220/phase-e/r5/review/independent-r5.json` and `.cache/v220/phase-e/r5/core.log`.

An isolated Gitea 28.3.0 server listened on loopback and hosted two real private repositories under distinct disposable accounts. A probe linked to the R6 Release Core objects validated both PAT identities, rejected a mismatched app binding and confirmed that a foreign PAT could not read the other account's repository. It listed an actual private pull request and read its details, commit and changed file. GitService Clone, the read-only Fetch connection check and a reviewed Fetch succeeded through a fixture-native Git helper. Clone of the other account's repository failed. The stock Hosting transport rejected the fixture CA. The successful API probe anchored that CA inside its test URLSession, and Git used a process-specific CA file. The service, tokens and certificate keys were removed. This covers a real isolated private server. External organizations and OAuth require separate validation.
