# Development

GitPier is a native Swift / SwiftUI / AppKit macOS application. See [Contributing](../CONTRIBUTING.md) for change requirements and [Architecture](architecture.md) for module boundaries.

## Environment

- macOS 14 or later; Xcode 16 or later with a Swift 6 toolchain and command-line tools. `Package.swift` declares Swift tools 6.0. The CI workflow uses the toolchain supplied by its `macos-15` runner; Swift 6.1.2 compatibility is part of the existing validation baseline. A newer local compiler alone does not establish CI compatibility.
- A working Git, SSH, and an installed shell. Git LFS and Codex CLI are optional external installations, with their own configuration and authentication.
- Swift Package Manager. Keep `Package.resolved` for reproducible dependencies.
- Python 3.9+ for metadata, validation, and release-tool scripts; no third-party Python packages are required for these scripts.
- `codesign`, `hdiutil`, `osascript`, and Finder for local packaging and installer acceptance.

Check the selected toolchain with `xcodebuild -version`, `swift --version`, and `git --version`.

## Build and test

Run from the repository root:

```sh
Scripts/build-app.sh
Scripts/test.sh
```

The build script produces `dist/GitPier.app` for the current architecture, including the CLI helper, Sparkle framework, resources, and legal notices. It regenerates icon assets from the canonical PNG, verifies the bundle, and uses ad-hoc signing by default.

```sh
CONFIGURATION=debug Scripts/build-app.sh
UNIVERSAL=1 Scripts/build-app.sh
Scripts/test.sh --filter GitServiceTests
```

To preserve an existing local app, set `GITPIER_APP_OUTPUT_DIR` to a separate absolute output directory. Build caches remain in `.build` and `.cache`. Scripts use SwiftPM's native build engine; newer toolchains may report its deprecation. Do not change release settings or dependency versions just to build locally.

Core tests use disposable repositories. Credential tests may create synthetic Keychain entries and must clean up their own entries. Do not run destructive tests against personal repositories or change global Git/SSH configuration.

## Native acceptance

A logged-in macOS GUI session is required for UI / PTY acceptance:

```sh
Scripts/ui-acceptance.sh
GITPIER_UI_ACCEPTANCE_SCOPE=scrollbars Scripts/ui-acceptance.sh
```

Use the relevant scope supported by `Sources/GitPier/UIAcceptance.swift` and its acceptance extensions. Exercise changed workflows with temporary repositories and isolated application state. Real mouse, keyboard, scrolling, window lifecycle, or OS authorization behavior needs native interaction; offscreen renderings and model assertions do not establish those results. Captures default to `.cache/ui-acceptance`.

Performance fixtures are generated by `Scripts/performance.sh` and write local measurements under `.cache/performance`. Never infer general speed claims from one synthetic fixture.

`Scripts/product-screenshots.sh <absolute-output-directory>` builds isolated fictional repositories for native product captures. Pass an explicit local output directory, review every image for private data, and publish only selected final assets.

## CI

The workflow is [Validate macOS](../.github/workflows/validate.yml). Its planning job runs the CI-policy and cache-policy regression suites, then selects full macOS validation, a narrow documentation check, or reuse of a successful full run for the exact same commit.

The documentation route permits only its explicit Markdown allowlist. Media, ignore rules, scripts, packaged notices, resources, or unknown paths select full validation; a repository-cleanup change that includes media must not be represented as a Markdown-only CI run. The documentation check validates encoding, whitespace, conflict markers, and scope; it does not replace link or visual review.

Full validation retains the Core tests, release-tool checks, application build, temporary DMG structure, and signed application archive. Cache reuse changes build preparation, not test coverage. Tag reuse requires complete evidence for the same SHA. Read the actual runner/toolchain and final job results before claiming success.

Local policy checks:

```sh
python3 Scripts/test-ci-validation.py
python3 Scripts/test-ci-cache-inputs.py
python3 Scripts/test-release-tools.py
```

## Packaging and updates

Release metadata has one source: `Sources/GitPier/Resources/ReleaseConfiguration.json`. Preserve its production Bundle ID, feed URL, and update public key unless a separately reviewed distribution change requires otherwise.

```sh
UNIVERSAL=1 Scripts/package-release.sh --unsigned-candidate
Scripts/test-dmg-structure.sh
```

The first command creates a local candidate, not a published or production-update-signed release. The structure test uses its own temporary app/image and mount; it does not prove Finder layout or installation behavior. Review `Scripts/package-dmg.sh`, `Scripts/sign-release.sh`, and `Scripts/verify-release.py` before authorized distribution work. Production update keys belong in the maintainer's Keychain with separately protected backups, never in source, logs, or CI. Key backup, signing, upload, and publication require explicit authorization.

Current distribution uses Universal DMGs and ad-hoc code signing. Developer ID signing, notarization, and production Hardened Runtime adaptation are future work. Sparkle authenticates signed update metadata and packages independently of Gatekeeper. Changes to distribution need bundle/signature validation, a real Finder layout check, and an isolated update/relaunch test as appropriate. Never disable trust checks to make acceptance succeed. See [Security](../SECURITY.md#updates-and-distribution).

## Hosting setup

Ordinary GitHub.com and GitLab.com users can use the bundled public OAuth registrations or a PAT. GitPier has no token relay/backend or embedded client secret. Git network credentials remain independent of hosting API accounts.

Self-hosted GitLab and Gitea require a public OAuth client registered on that instance. In Settings → Code Hosting, enter the HTTPS instance URL (including any installation prefix/port), Client ID, and callback configuration. Public Client IDs identify applications and are not credentials.

| Provider | Callback / flow | Limits |
| --- | --- | --- |
| GitHub.com | Device Flow in the default browser | Enable Device Flow in the public registration; no local callback listener is used. |
| GitLab.com / self-hosted GitLab | `gitpier://oauth/gitlab`, public non-confidential client, S256 PKCE | Register the exact callback. Self-hosted configurations can instead use a supported fixed loopback port, such as `http://127.0.0.1:43827/oauth/gitlab/callback`. |
| Gitea | `http://127.0.0.1/oauth/gitea/callback`, public client, S256 PKCE | The app chooses an available loopback port. Granular-scope OAuth requires recognized Gitea 1.23+; otherwise use PAT. Server policy still applies. |

A PAT must belong to the selected instance and have permission for the requested repository and action. Start with read permissions. GitHub collaboration uses `public_repo` or broad `repo`; GitLab writes require broad `api`; Gitea repository writes and issue comments need their respective scope categories. The expanded review/comment option requests both Gitea write categories. Existing permissions are not silently enlarged. A conflicting prior Gitea OAuth grant can require owner-managed reauthorization or PAT replacement; GitPier does not revoke it automatically.

PR/MR lists, details, commits, files, conversations, and CI load on demand. Creation requires a pushed branch and confirmation. GitHub supports native review decisions and supported line/range comments. GitLab Discussions, replies, resolution, and approvals use separate operations and permissions; partial results are not atomic. Gitea formal review creation/approval/request-changes/pending submission and unverified inline placement use browser fallbacks; ordinary comments and supported existing-thread replies remain available. Reviewer requests are additive where supported on GitHub/Gitea. Capabilities and permissions are checked per target; a successful login does not establish private repository access or every server-version capability.

Unknown write results retain recovery metadata and block automatic resubmission. Inspect the platform and acknowledge the result explicitly. Test private servers, OAuth callbacks, review permissions, and CI access on authorized disposable repositories; mocks do not establish real-service acceptance. Credential storage and disconnect/migration limits are described in [Security](../SECURITY.md#credential-storage).

## Documentation and assets

The [README](../README.md) introduces the product; [CHANGELOG](../CHANGELOG.md) retains release history. Public guides should describe durable user or contributor needs. Keep English/Simplified Chinese UI strings and both READMEs aligned. Internal plans, execution logs, measurements, acceptance reports, and authoring projects belong in ignored local directories; they are not a substitute for a separately protected backup.

Publish only reviewed final media, preserve applicable notices, and keep authoring dependencies out of the Swift application. Application-owned scrollbars reuse the shared Diff overlay implementation across both axes, nested editors, and presentation roots. New windows/sheets install `AppAppearance`; popovers install `AppPopoverAppearance`. About remains the rightmost Settings tab with stable selection IDs.
