# GitPier v2.1.0 implementation plan

This is the historical implementation plan for [v2.1.0 (35)](https://github.com/Heisenberg2024/gitpier/releases/tag/v2.1.0). The release was published on 2026-11-03. [Publication evidence](development.md#v210-publication--2026-11-03)

**Goal:** Finish the existing native workflows, preserve uncertain operation results, reduce repeated multi-repository work, and remove the standalone Hero Demo.

**Architecture:** Extend the existing `GitService`, `OperationResult`, `OperationCenterHistory`, `RepositoryModel` and context advice. Keep the current per-worktree FIFO/common-directory queues, authentication, Index review and AppKit/SwiftUI presentation. No new executor, journal, platform, dependency or application shell.

**Specification:** The owner's v2.1.0 goal objective, supplied 2026-11-02. It explicitly selects inline development on `main`, authorizes safe branch deletion and ordinary commits/push after validation, and excludes Tags, Releases, production installation/signing/notarization. The owner later explicitly authorized one read-only reviewer; that same reviewer completed the initial and corrective reviews without edits, builds or UI access.

## Global constraints

- Native Swift/SwiftUI/AppKit, Universal arm64/x86_64, macOS 14 minimum, existing locked dependencies.
- Preserve Bundle ID, icon, credential formats, Sparkle feed/key and historical releases/tags.
- Preserve external Index bytes, partial staging, Hooks, signing and TLS/SSH verification.
- Network verification is explicit and read-only; uncertainty never authorizes automatic Push or another Commit.
- Retain the compact context entry left of the branch; reuse original review/confirmation paths.
- Use existing semantic symbols, English/Simplified Chinese strings, native appearance roots and shared overlay scrollbars.
- Preserve unrelated edits, worktrees and ignored files. No new branch, reset, automatic stash, forced deletion or force push.

## Review focus

- An accepted Push may return an error/cancellation; only an exact remote/ref observation can confirm its checkpoint.
- Remote configuration, branch, HEAD or worktree identity may change during a query or before a retry.
- Later successful operations, refreshes, navigation or history pruning must retain an earlier unresolved checkpoint and diagnosis.
- Worktrees share configuration/queues but keep separate branch/Index/state identities.
- Large inventories and repeated no-op visibility updates must not multiply background processes or publish stale results.
