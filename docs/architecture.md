# Architecture and security boundaries

## Workflow observation and navigation (v1.7.0 development)

`OperationCenterHistory` is a pure in-memory event reducer. App-owned `OperationsCenter` bridges existing `OperationProgress` tickets, BatchFetchCoordinator updates and the existing Review journal's readback. Ordinary local refresh progress opts out. No Git execution queue, polling timer or duplicate journal is introduced; UI lifetime cannot own cancellation. UUID/revision checks reject stale/duplicate events; completed records cannot become active again. Normal recent summaries are capped at 100; automatic Fetch coalesces completed records per repository, while unresolved Review metadata remains governed by the existing journal. Recovery navigation captures and rechecks root/Common Directory, metadata directory filesystem identities, HEAD/Index/operation and remotes. Writes still run through their original confirmation and service checks.

`NavigationRequest` allows only versioned open/page requests. The distinct `GitPierCommandLine` SwiftPM product is packaged as the signed `Helpers/gitpier`; main/CLI product names must not differ only by case. Launch Services explicitly targets a bookmarked selected app. SwiftUI `onOpenURL` and AppDelegate feed the same serialized, UUID-deduplicated receiver. Existing windows prefer `gitpier://` external events. OAuth remains separately path/state/PKCE validated. The launcher and receiver both validate directory access and System Git working-tree identity. Installation uses descriptor-relative no-follow IO, exclusive names and a versioned private hash/bookmark receipt, without shell edits or same-name overwrites. Uninstall verifies current ownership and file identity.

The existing Quick Open sheet uses the `WorkspaceCommand` navigation vocabulary, memory recent commands and disabled reasons. Terminal shortcut protection and existing page IDs remain unchanged. Repository navigation stays in its existing toolbar and recovery banners; the duplicate Next Steps menu was removed after evaluating all conditional entries. CLI installation sections share the existing Terminal tab (3); About remains the rightmost tab (7). Explicit CLI navigation presents an existing workspace window, restores a minimized window, or defers presentation until the cold-start window hook attaches.

简体中文：操作中心只观察既有任务/批量Fetch/审查日志，普通本地扫描不记为任务，不新增写队列或日志。CLI只接受固定导航请求，通过原生Launch Services定位用户选定应用，冷/热入口共用去重顺序路由，OAuth继续独立核验。安装拒绝符号链接/同名覆盖，卸载验证归属；现有命令面板、终端焦点、Git确认与凭证边界保持。

## Review collaboration (v1.6.0 released; v1.6.1 stability candidate)

`HostingReviewModels.swift` adds typed provider capabilities, stable remote target/revision identities, code anchors, discussion comments/threads and memory-only review drafts. `HostingReviewAPI.swift` adapts native provider semantics using the existing HTTPS boundary. `HostingReviewSubmission.swift` owns immutable confirmation tickets, per-target serialization across windows, preflight revalidation, stable-ID readback and independent partial/unknown outcomes. These modules never enter the Git write actor or acquire its queue.

Native review sessions retain drafts across detail reconstruction. Timeline pages share `HostingRequestDetailCache` with the existing `HostingRequestDetailLoader`; writes invalidate only the affected request's collaboration/overview sections. The existing `DiffParser` and `DiffTable` retain local staging behavior. Remote review uses an independent line callback and complete patch/hunk hashes; no staging/discard/apply callbacks are provided. See [provider matrix, anchor validation and API limits](code-review.md).

`HostingReviewersAPI` uses provider-native candidate and additive-request APIs under the same submission coordinator. GitLab list-replacement writes are disabled. `HostingApprovalRules` reads GitLab rule state separately. `HostingReviewDashboard` provides explicit, paged account inbox queries and a 60-second memory cache; `HostingReviewShortcuts` reuses the Hosting network budget and validates source repository/project, branch and full SHA before opening a request. Branch comparison retains the existing local Git path and tracking-snapshot provenance.

`HostingDisconnectionIntentStore` persists one private file per disconnected account adjacent to hosting metadata. It is written before the first asynchronous suspension, overlaid at metadata load and removed only after main metadata has committed the disconnected/cleaned state. Cleanup progress merges monotonically; failed persistence retains a recovery row, and total persistence failure pauses credential deletion while revoking the in-memory session.

GitPier is a native macOS application built as a SwiftPM executable. `GitPierCore` contains models, status/diff parsing, process execution, Git operations, persistence, Keychain access and FSEvents watching. SwiftUI coordinates views; AppKit provides the commit text editor, virtual Diff table and SwiftTerm PTY view. `PTYSupport` contains bounded native process/session cleanup.

## Review operation recovery (v1.6.1)

`HostingReviewOperationJournal` is a synchronous, bounded, versioned DTO store called inside the existing `HostingReviewSubmissionCoordinator` actor. Per-confirmation batches retain all items without bodies or anchors. The coordinator persists a batch and each item's possibly-sent transition before invoking the write closure, then checkpoints the receipt before readback and the verified result after strict validation. Failure to save an intent prevents sending. Failure to save a receipt/final state preserves the earlier uncertain barrier. Descriptor-relative private IO checks file ownership/mode/type and synchronizes same-device parent namespaces, then requires file fsync → atomic rename → checked directory fsync → macOS F_FULLFSYNC. These are journal-only opt-ins to the existing private-directory helper; default credential/disconnect writes retain their behavior. Unsupported barriers fail closed. Checked enumeration distinguishes an empty store from an unreadable one. Unknown states never expire or automatically replay.

`AppStore` injects a journal beside its workspace into the single review registry shared across windows. `HostingReviewRecovery` shows startup disk recovery without contacting any platform. User-triggered receipt inspection uses an explicitly chosen existing binding, current account and fresh stable target/revision checks; it yields metadata evidence and retains the barrier because bodies/anchors were never persisted. Manual acknowledgement is durable and requires a separate UI confirmation. Disconnect permanently invalidates the account's old sessions before suspension, clears private memory and prevents late results from repopulating it. The journal does not participate in Vault/Keychain restoration or the Git write queue.

The coordinator overlays live unresolved results and failed acknowledgements on disk snapshots when a replacement succeeded but its final durability barrier failed. Completed-history cleanup excludes those batches. A successful explicit acknowledgement retry, or complete live receipt reconciliation with a successful verified checkpoint, clears only the corresponding pending barrier.

Disconnect and registry shutdown also discard cached coordinator reports and revision contexts, retaining only stable consumed-confirmation/unknown item IDs. A late task cannot repopulate the private report cache, restart a discarded submission or erase its durable uncertainty. Other accounts and new confirmations remain independent. An already running task or HTTP request can own its payload until cancellation/response settles; this is cache lifecycle control, not secure memory erasure. Explicit draft discard clears obsolete composer/confirmation snapshots as well.

Write exclusion uses the remote provider/instance, stable remote user, repository ID and request ID. Reconnecting the same remote user with a new local account UUID cannot bypass an active/unknown operation. Credential access, recovery receipt inspection, per-account listing, acknowledgement and payload cleanup continue to require the original local UUID. Different remote users/instances remain independent; acknowledging one local identity does not dismiss another identity's unresolved record.

简体中文：日志复用既有提交协调器，在逐条发送前持久化最小意图，取得结果 ID 后和完整回读成功后分别检查点；持久化失败不能授权发送或消除未知保护。跨窗口共用一个协调器；启动仅恢复本机元数据，平台回查由用户主动选择关联并严格核实稳定身份。正文/位置不落盘，回查只是元数据证据，仍需人工核实。断开同步永久失效旧会话，拒绝迟到响应恢复私有状态，与凭证和 Git 队列独立。

## Ownership and state

`AppStore` is shared by application windows. Each canonical working tree has one `RepositoryModel` and one `GitService` in the registry. Drafts, tabs, selected files, directory expansion and terminals belong to that repository, never to a global draft. Repositories and preferences persist in `~/Library/Application Support/GitPier/workspace.json` with atomic replacement and mode 0600. Invalid configuration is preserved and further writes are blocked rather than silently replacing it. Repository array order is persisted and shared by the sidebar and organization pages; drag-and-drop reorders within a group without changing identity, drafts or credentials. Recent-use timestamps affect only explicit recent sorting. Organization-scoped Open actions assign new and existing repositories to that group. An isolated configuration file can be selected with `GITPIER_WORKSPACE_FILE` for acceptance tests.

The Git actor's explicit FIFO write queue spans async suspension points. Actor isolation alone would allow interleaving writes while awaiting child processes. Git's own locks still protect against external clients. Read refreshes use `GIT_OPTIONAL_LOCKS=0`. `write-tree` runs against an Index copy; object-directory events are ignored because Git can freshen immutable object timestamps. Index, HEAD, refs and working-tree events remain watched, with debounce when watching is enabled. Watching marks pending changes only. Repository clicks, application foreground activation, explicit refresh and completed writes read fresh Git state. Foreground refresh covers the current repository or visible dashboard collection; activation reads are skipped during writes, whose final refresh covers the change. Requests are coalesced, unchanged state is not republished, and appearance/font changes do not trigger Git commands.

Status uses porcelain v2, branch headers and NUL-delimited UTF-8 paths. Renames consume their separate original-path record. Non-UTF-8 paths fail explicitly rather than being decoded into potentially wrong paths. Literal pathspecs and `--` separators prevent filenames from becoming Git options or pathspec expressions.

## Workspace overview (released in v1.4.0)

`WorkspaceSnapshot.swift` contains local card values; `WorkspaceStatusService` owns an in-memory cache keyed by stable repository ID, separate from `RepositoryModel` and persisted configuration. Monotonic configuration revisions reject delayed metadata reconciliations, so removed/moved entries cannot be resurrected by an older app task. Card names/groups/favorites come from the current records. A bounded sequence of local Git queries verifies the working-tree root, resolve Git/common directories, read porcelain v2 counts/HEAD/upstream/local tracking refs and list remote names and inspect partial-clone configuration. Operation markers are read from the working tree's metadata. It does not construct Index trees, Diffs or history, and local queries disable Git's lazy fetch. Partial clones require Git 2.43 or later for this guarantee; older Git still supports ordinary repositories and receives a clear local-query error for partial clones. Capability checks coalesce per executable identity. Deleted nested metadata cannot silently fall back to an ancestor repository.

The status actor has three workers, merges repeated requests, prioritizes visible/manual requests and uses generation tickets. Invalidated/cancelled jobs retain their worker slot until completion, and late results cannot repopulate removed records or overwrite newer scans. Entries distinguish unscanned/queued/collecting/fresh/stale/failed, with missing directory, invalid repository, permission and Git-query failures. Failed scans preserve the old display snapshot while summaries exclude its unavailable data until a successful scan, even during invalidation/retry. Cache lifetime is 30 seconds on requests, including failed-attempt backoff so configuration saves do not constantly rescan unavailable repositories; explicit refresh can bypass it. View changes do not clear the cache. No snapshot, search query or authentication result is persisted. Optional FSEvents watching remains opt-in and marks entries stale; explicit refresh, foreground activation, changed foreground-session status and completed writes request fresh local scans.

`WorkspaceModel` is the AppStore-owned observation bridge. `DashboardView` uses the same `WorkspaceFilter` rules for counts and AND-combined filters, preserves repository array order/drag behavior, and distinguishes registered workspace entries from known common-directory groups and unresolved entries. Linked worktree drafts, terminal/layout state and lifecycle ownership stay in their existing models. Startup renders Dashboard before all scans and does not activate each repository session.

`WorkspaceOperationBudget` caps workspace scan/search/Fetch operations at three concurrent permits; each operation executes Git commands sequentially. `BatchFetchCoordinator` permits two Fetch jobs and keeps per-target results across page changes. Reviews resolve remotes with existing authentication, fingerprint full remote configuration/effective URLs plus common-directory filesystem identity and revalidate before execution. Matching common-directory/remote/configuration targets merge their selected IDs; differing worktree remote configurations remain separately reviewed and serialized. Fetch uses the canonical worktree FIFO and common-directory queue with `--no-write-fetch-head`, no recursive submodule Fetch and no opportunistic auto-GC; existing network operations also coordinate shared metadata. Pending FIFO/common/budget waits are cancellable without disturbing queue ownership/order. Failures do not rewrite remotes, clear Index or chain other operations.

`WorkspaceSearchService` uses rolling groups of at most three workers and the shared budget. Metadata matching reuses current entries. User-requested tracked paths use controlled case-insensitive Git pathspecs with escaped user glob characters; NUL output is validated and capped at 4 MiB. Commit searches use literal native message matching or validated hexadecimal hashes, at most 25 results per type/repository/page by default (50 configured maximum, with one possible exact-hash hit), and 2 MiB output. Queries are bounded to 512 UTF-8 bytes, UI input is debounced 250 ms, and cancellation/generation checks reject old responses. There is no source-content index or remote search. `QuickOpenView` uses existing records, recent timestamps and favorites; native key handling belongs only to its sheet, and the workspace ⌘⇧P route excludes terminal/confirmation/sheet focus.

## Automatic remote checks (released in v1.4.2)

`RemoteCheck.swift` separates remote phases and success/attempt/eligibility dates from `WorkspaceSnapshot.collectedAt`. A snapshot resolves the branch's upstream Remote and its common-directory/configuration identity with local queries; failed identity resolution does not discard local file/count data. The record key is SHA256 of the existing Fetch identity (canonical Common Directory, Remote name, full remote/effective URL config and filesystem identity). Same-configuration Worktrees share it; each Worktree retains its own branch comparison.

`WorkspaceModel` observes the same `BatchFetchCoordinator` for manual and automatic tasks. `AppSettings.automaticFetch` defaults false; interval is 15 minutes for the selected repository (10/30/60 configurable), 45 for others when scope is workspace. Startup waits five seconds; lifecycle events debounce two seconds and a 15-second foreground/online tick reevaluates eligibility. Other repositories rotate through bounded candidate batches and admit at most two targets every 30 seconds. Success deadlines adapt when a Worktree becomes current. Monotonic deadlines protect the running process from wall-clock jumps; persisted dates seed bounded deadlines across restarts. Failures back off 300/600/1200/2400/3600 seconds; authentication pauses until an explicit Retry or a relevant credential-change event. Backgrounding/disabling cancels automatic tasks; manual operations cancel and await automatic transport before entering existing Git queues.

`GitService.checkedWorkspaceFetch` is the shared implementation. Automatic tasks require standard tracking refspecs, reject Mirror/multiple URLs and preserve no-tags/no-prune/no-FETCH_HEAD/no-submodules/no-auto-GC protections. Authentication is native across transports, as detailed below. GitPier-owned credential readers retain their dedicated no-UI policy; native configured helpers and SSH keep their own authorization behavior. Manual operations retain existing semantics. The older v1.4.3 blanket no-UI replacement is superseded for native authentication by the owner's explicit direct-reuse requirement.

Adjacent `workspace.remote-checks.json` uses a versioned envelope, atomic replacement and 0600 mode. It stores opaque key/UUID/date/phase/failure data, never URLs, tokens or server diagnostics. Invalid/unknown files are preserved and further writes blocked with a Settings warning. Deleted repository records are removed from history. Completed Fetch requests refresh only the affected Common Directory snapshots; open sessions accept ahead/behind updates only when path/HEAD/branch/upstream still match and the snapshot uptime is newer than the session read. Pending snapshots survive an in-progress refresh/write. Retained batch completions cannot overwrite a later native-button attempt because monotonic attempt order is checked. Running cancellations refresh tracking counts because Git may already have committed refs; queued cancellations do not scan. Diff, history, drafts and page state are untouched. Zero/zero comparisons are always described as matching tracking refs; a separate state/time reports remote checks, including custom manual refspecs that may not cover every upstream. Native Fetch records success only for unchanged targets actually included by --all (respecting skipFetchAll and skipDefaultUpdate). Manual queue acceptance explicitly controls which selection IDs can be removed; automatic work never touches selection.

## Authentication capabilities (v1.4.4)

Automatic Fetch uses native Git authentication across hosts and protocols. `GitService.checkedWorkspaceFetch` no longer runs password/Agent preflight: Git connects first and asks for credentials only when the transport requires them. Anonymous public access, HTTP headers, OAuth credential fields and SSH file identities are therefore not incorrectly blocked. Fetch success sets `BackgroundAuthentication.verifiedByFetch`; local Retry only admits an attempt and never records server success.

`safeCredentialArguments` replays the complete ordered helper multivar, with URL keys and empty resets. `SafeCredentialHelper.getOnly` follows Git's documented helper transformation (`!` snippets, absolute commands, otherwise `git credential-...`) inside an isolated shell, forwarding protocol stdin/stdout unchanged while accepting only get. Names and hosts are not allowlists. Existing core.askPass, GIT_ASKPASS and SSH_ASKPASS providers retain native precedence; only GitPier's fallback UI is replaced with a refusal. This preserves helper/account/path matching, partial responses and OAuth fields, while preventing Git-driven store/erase after rejection. Native helpers may perform their normal refresh/storage internally. Managed GitPier HTTPS Tokens retain their no-UI dedicated reader and explicit foreground authorization; protocol/host/account isolation remains.

Automatic SSH inherits the original `core.sshCommand`, `GIT_SSH_COMMAND`, `GIT_SSH`, variant, SSH config, Agent, file identities, native Keychain and providers. It does not append the old restrictive -F/UseKeychain=no configuration or require an Agent inspection. Terminal login and GitPier fallback login UI are disabled; original configured Askpass providers remain available, and cancellation/timeouts remain bounded. Optional explicit SSH preparation still uses conservative inspection and an Agent; private sockets are bound by canonical repository and selected authentication identity, so preparing one repository cannot mask another's inherited Agent.

`upstreamFetchTarget` follows the configured branch remote, then Git's single-remote/origin default, including detached/unborn branches and init/push without tracking configuration. Workspace collection creates a target whenever an unambiguous remote exists; it remains local-only. No remote produces no automatic target. Mirror/multiple-fetch-URL and unsafe refspec restrictions remain to prevent automatic local-branch/tag changes.

AppStore Clone writes the selected CredentialProfile into the new RepositoryRecord before saving/reconciling/selection; normal repository opening retains original Git configuration. Standard Homebrew PATH locations are appended without changing inherited precedence. No shell startup script, global Git/SSH configuration, credential migration or ACL changes occur. Existing credentials must be reachable by the application's Git process; another terminal's private transient environment is not imported.

Compatibility metadata version 3 rechecks old unsupported/foreground/missing-credential/SSH-preflight/configuration blocks and transport skips once. Real AccessDenied/ServerRejected and current-version failures remain paused; successful history and normal intervals are preserved.

## Reviewed commits

Commit inclusion checkboxes are local repository state, separate from row highlighting and the real Index. On Commit, the Git actor validates the reviewed live snapshot, stages only selected files that have no staged content, and preserves the existing content of partially staged files. A private Index copy restores unchecked staged paths to HEAD (or removes them from an unborn Index). Normal `git commit --file=-` then operates on this exact chosen tree. Existing unchecked staging stays in the live Index, which is never replaced. Preparation staging remains available if commit or hooks fail.

Temporary hook wrappers delegate original hooks and signing. The final `commit-msg` gate separately checks the chosen commit tree, a fresh copy of the expected live Index tree, and HEAD. Those trees can differ when there is unchecked staging. Post-commit/post-rewrite hooks use the live Index. Reviewed cached patches for unstaged files are checked again before staging; external Index/HEAD changes require another review. No whole-working-tree add or `commit -a` is used.

External Index or HEAD changes mark the UI as requiring another review. A race after the final gate cannot insert external staged changes into the isolated commit; their live Index entries remain available. The commit phase is allowed to finish atomically; cancellation remains available for other commands. Hooks are trusted repository code and can perform arbitrary actions, just as with Git itself.

Hunk application checks the patch first and uses atomic `git apply`, with an Index snapshot check. Rename/mode/submodule and whitespace-filtered hunks are deliberately restricted to file-level staging. Discard and history rewrites require explicit UI confirmation.

Push uses Git's porcelain output to identify a single current-branch rejection with `fetch first` or `non-fast-forward`; authentication, remote policy, force and multi-destination/ref failures retain their error flow. `PushRejection` captures the original branch/HEAD and actual push URL/ref. After the user confirms Merge & Push, one actor write queue spans fetching that destination, merging the fetched commit and retrying the push. Fetch uses a unique temporary ref with `--no-write-fetch-head`, resolves its commit and deletes the ref, so another Git client's `FETCH_HEAD` cannot redirect the merge. Recovery rechecks branch/HEAD and requires clean tracked content with no unfinished operation. Merge explicitly disables autostash and uses `--no-edit --ff`, independently of pull/rebase/ff-only preferences, while retaining hooks, signing and transport verification. Conflicts retain the merge state and stop the push; no automatic stash, force or conflict resolution occurs. Users resolve and continue the merge before retrying Push. A cancelled confirmation performs no Git writes or duplicate commit.

## Conflict resolution

`ConflictSnapshot` reads literal NUL-delimited unmerged Index entries and stage 1/2/3 blobs. It captures branch/HEAD, operation metadata and a streamed SHA256 fingerprint plus permissions of the working file. `ConflictMarkers` preserves line terminators and UTF-16 editor ranges for merge, diff3/zdiff3 and configured marker sizes. The repository-owned `ConflictEditorModel` retains drafts per file, rejects stale snapshots and never writes while choosing blocks or typing. The native page shows Current/Incoming, an optional base preview and an editable result; previews and results use the shared scrollbars and Diff font settings.

`GitService.resolveConflict` validates the snapshot in the canonical worktree's write queue before writing and staging only the selected literal path. Text results reject remaining markers, retain CRLF when appropriate and preserve permissions. Whole-version choices use `checkout-index` so Git filters and checkout semantics remain active; deletion is explicitly confirmed. Text editing is limited to 1 MiB UTF-8; binary/large regular files support whole-version/deletion choices, while symlink, gitlink and file-type conflicts remain available for external resolution. Other Index entries and partial staging are preserved.

Once all conflicts are resolved, `MergeReview` captures the full reviewed Index, merge parents and message. Completing the merge reuses the private Index and original hooks/signing checks, including a merge-parent check at `commit-msg`; unchanged-tree merges are supported. The UI disables continuation/push while conflicts remain. A merge-and-push recovery keeps its original destination across conflict resolution and failure retries; completing the merge never creates another copy of the original local commit.

## Interactive Rebase (v1.3.0)

`InteractiveRebase.swift` holds typed plans, message grouping and fixed temporary editor helpers. Git commands remain in `GitService.swift` and the existing canonical-worktree FIFO. Native `rebase -i` receives only reviewed full commit IDs and supported actions; messages are data files, never shell source. Plans require a clean branch/Index/worktree and a bounded linear ancestor range, reject merge histories, and freeze local remote-tracking sharing evidence. A missing remote-tracking match does not establish privacy.

The service fingerprints HEAD/branch, Index stages, native todo/done/original HEAD/messages, and changed working files before controls. Git metadata is authoritative after interruption/restart. A private `gitpier-rebase-messages.json` preserves approved messages; helpers are recreated in a mode-0700 temporary directory and removed after each process. Git's hooks, signing, reflog and native Abort remain active. A corrupt message plan blocks continuation but cannot block reviewed native Abort. Signing/hook failures retain Git's actual diagnosis and recovery state; some require an explicit terminal recovery commit before native Continue, never a signing bypass.

## Selected-line staging (v1.3.0)

`SelectiveStaging.swift` builds exact selected text patches using the shared Diff's replacement pairing. Unstage starts from the complete staged Diff's new side, so context matches the current Index even when other staged changes remain. CRLF and no-final-newline markers are retained; unsupported metadata/filters/encodings and files beyond the shared Diff bounds fail explicitly. External Diff and text conversion remain disabled, while safe native heading drivers can be retained.

The existing Git actor holds an exclusive, task-owned real `index.lock` while native `git apply --check` / `--cached` operate on a private Index copy. HEAD/branch, original Index bytes, working-file fingerprints and the original patch are revalidated before an atomic same-directory rename. Other clients' locks are never removed; failure/cancellation leaves the real Index and working files intact. `SelectiveStagingUI.swift` adds gutter clicks and keyboard actions while the code NSTextView retains selection/copy. Selection uses fixed file/revision/Index tickets and clears on refresh; support checks run in the background, and highlighting reloads visible rows only.

## Patch, LFS and Submodule workflows (v1.3.0)

`PatchWorkflow.swift` parses bounded Git Diff inputs and native NUL-delimited summaries. `PatchWorkflowView.swift` owns local dialogs, preview and confirmation state. Working Tree and Index targets are independent; encoded input is limited to 8 MiB / 200 files, literal binary files to 8 MiB and total decoded binary data to 32 MiB. Mail input, binary deltas, rename/copy/symlink/gitlink and repository metadata/nested-repository paths fail explicitly. Index imports reuse IndexEditTransaction; worktree imports retain native applicability/atomic-hunk checks without reject, three-way or unsafe-path fallbacks. Export resolves immutable commits and distinguishes Diff from format-patch emails.

`GitLFS.swift` holds Pointer, JSON and root-attribute models. Rule edits preserve unselected bytes/attributes and Index staging, append explicit tracking definitions and remove only direct LFS tokens when untracking. Network operations remain in GitService with existing authentication and real progress decoding. Pull performs fixed-ref native Fetch, revalidates HEAD/Index/configuration, then checks out through a private Index under the real Index lock. Filters must already be configured; no install, migration, pruning or auto-staging runs. Large downloads use a cancellable one-hour process bound. Native file lists show at most 5,000 entries.

`Submodule.swift` holds native config/gitlink parsing and typed reviews. Listing caps 100 entries / three nested levels and verifies child top-level identity instead of mistaking parent fallback for initialization. Mutations use the parent's common-directory queue plus the registered child's FIFO/common queue; a common directory already held by the parent is not acquired twice. Recorded update fixes the Index gitlink, remote update fixes a reviewed ls-remote SHA, and native detached checkout refuses ignored-file overwrites. Add downloads first, revalidates parent/index/.gitmodules state, then registers/stages only the config/gitlink and verifies other Index entries. Existing directories, residual metadata, relative remote Add URLs and dirty/filtered config fail clearly. Nested mutation requires opening the immediate parent; deinit/remove are not exposed.

## Authentication

`GitService.safeCredentialArguments` delegates all configured helper forms through a get-only wrapper, preserving Git's native command rules and credential protocol. Literal helper recognition is used only for display. There is no provider-specific permission adapter or automatic helper allowlist. The real Fetch decides whether authentication is required; source readiness is separate from a verified remote result. Native SSH authentication is inherited rather than rebuilt.

Keychain uses generic-password items under `GitPier.credentials`, keyed by UUID. Configuration contains only profile name, host, username, protocol and SSH identity path. Managed HTTPS profiles reset the helper chain for that process and install the GitPier helper using a quoted executable path and profile UUID. Tokens are read only in the helper and returned through stdout to Git's private credential pipe. `store` and `erase` do not copy secrets into files. HTTPS profiles answer only for their configured host and refuse HTTP.

The SSH helper resolves aliases with `ssh -G`, validates the configured host, then replaces itself with system SSH and the selected identity. It preserves SSH config, agent and verification. GUI AskPass handles interactive prompts. Git errors redact credentials embedded in pre-existing HTTPS URLs. No global Git, SSH or shell configuration is written automatically. Local identity/signing/hook save buttons are explicit user actions.

## PTY and lifecycle

SwiftTerm 1.20.0 creates the controlling PTY, performs terminal emulation and synchronizes dimensions. Interactive login shells load their normal configuration. The terminal view and process are owned by `TerminalSession`; SwiftUI presentation can detach and reattach the same view. Hiding and repository switching retain sessions and buffers. Resizing uses global-pointer coordinates, disables implicit animation and publishes only WorkspacePanels live layout; RepositoryRecord and JSON are updated at drag completion. The same native terminal view is retained and font setup is cached; duplicate, zero and subpixel frame-size transitions are ignored. Diff rendering uses document revisions, cached fonts/line widths and no fixed-row height invalidation. Wrapped-row visible heights update during dragging and full heights are deferred until it settles. UnifiedScrollbars installs OverlayScrollbars on application-owned native scroll views after layout at the end of UI event cycles without timers or method swizzling, prunes virtualized documents, and rebinds geometry observers when documents change. Scroll views retain their original clip views, documents, scroll proxies and scroll-memory observers. SafeTerminalView uses the same OverlayScrollThumb through SwiftTerm’s public scrollback API, hides the native scroller, follows terminal foreground colors for independent theme contrast, and preserves its PTY and alternate-screen behavior. System file choosers retain AppKit scrolling. All application scrollbars use 6-point overlay thumbs; horizontal thumbs stay 56 points long and vertical thumbs stay 150 points long, shortened only when the viewport is smaller. Both fade after scrolling pauses. A separate clipped overlay follows the final code viewport in scroll-view coordinates and excludes the table header; Index thumbs sit on the left and working-tree thumbs on the right. An unstaged comparison with no old-side content shows the working tree at full width; staged and existing-content comparisons retain both sides. No terminal output logging is enabled. Session close hangs up its controlling session and stops the shell; application shutdown stops all owned sessions. Process cleanup checks session membership/ancestry and process start time before signaling descendants.

## Distribution

This is a **non-sandbox** desktop tool. It runs with the logged-in user's privileges, accesses user-selected repositories and launches Git, SSH and shell programs. macOS privacy prompts and filesystem permissions still apply. Git hooks and shell startup files are executable user code. Sidebar repository removal affects only GitPier records and associated sessions. The separate, explicitly reviewed Worktree removal operation described below can remove a clean GitPier-created linked directory.

`Scripts/build-app.sh` builds SwiftPM, packages the executable/resource bundles, creates ICNS from the AppIcon catalog, binds it through Info.plist, includes dependency notices, and verifies a local signature. `AppResources` resolves Contents/Resources for packaged application assets and falls back to SwiftPM's resource bundle during development. The default CoreGraphics terminal renderer does not need Metal shader lookup. Bundle roots contain only Contents, so signature sealing remains valid. The stable production bundle identifier is `com.heisenberg2024.gitpier`; existing workspace data stays in its original GitPier support directory. Signing identity is optional; default is ad-hoc. The repository is public. Builds never create a release, Developer ID signature or notarization automatically.

The CI workflow targets macOS 15 and runs the test and application build scripts. Universal packaging builds arm64 and x86_64 binaries with a macOS 14 deployment target. Compilation does not establish Intel or minimum-OS runtime compatibility; those require separate device checks.

## Operation progress and performance

ProcessRunner waits on termination/cancellation signals and streams stderr while preserving output limits and timeout escalation. GitProgressDecoder accepts only known Git stage counters, buffers bounded partial lines and throttles updates. OperationProgress is independently observed by the footer; operation/stage tickets reject stale transfer callbacks and commit remains protected from cancellation. Unknown stages never display invented percentages. Completed progress clears transfer counters. Completion banners filter transient Git transfer lines while keeping final results and diagnostics; commit-and-push reports both outcomes and only sends its completion notification when the full operation ends.

RepositoryFileIndex is built off the main actor when file status changes. Sorting, counts, path lookup and filter results are reused; history requests are coalesced and graphs constructed off the main actor. Diff caching protects the current and recently interacted keys within its budget. Workspace views reuse their native containers while repository-owned drafts, layouts, expansion and scroll positions remain separate. Optional performance instrumentation records command categories and timings only; it is disabled in normal launches. The destructive benchmark entry point rejects anything except the generated, marked temporary fixture.

`Sources/GitPier/Resources/ReleaseConfiguration.json` supplies version, monotonically increasing build number, macOS requirement, stable bundle identifier, feed URL and public update key. Sparkle 2.10.0 is pinned through SwiftPM. A successful SwiftPM link alone is insufficient acceptance.

One AppStore-owned UpdateManager serves About and the application menu. Sparkle's standard driver owns release notes, download progress, verification, installation and relaunch. Automatic checks default to off; automatic downloads/install-on-quit and system profiling are disabled. v1.3.0 restores standard scheduled-update presentation instead of suppressing it in favor of a transient notice. Immediately after updater startup, an already opted-in user receives one native background check; subsequent scheduling, last-check preferences and skipped versions remain owned by Sparkle. A missing production public key prevents updater startup. Native windows inherit the app-selected appearance; Sparkle language follows app-owned preferences after restart. Production entries must use fixed-version HTTPS GitHub Releases DMG URLs and numeric build versions. Signed feeds and validation before extraction are required; feed-signature failures never expire into a fallback mode (`SUSignedFeedFailureExpirationInterval=0`).

The stable feed is `https://github.com/Heisenberg2024/gitpier/releases/latest/download/appcast.xml`. Each future stable release must include the final DMG, its portable SHA256 file and the signed appcast. v1.0.3 has no appcast/updater and needs one manual DMG upgrade. Drafts and prereleases must never become the stable feed. Signed metadata and DMG hashes are immutable after signing.

Installers use hdiutil HFS+ / LZFSE (ULFO) and a Finder icon-view layout. Background resources contain guidance only; GitPier.app and the /Applications symlink are real drag targets. Packaging fails when Finder or its saved layout is unavailable. Mount/signature verification is separate from visual and drag-install acceptance.

Quit and last-window close block ongoing Git operations and clone tasks. Sparkle relaunch is postponed during work and resumed by explicit user action. Existing unsaved-conflict and terminal-job confirmation remains on the normal termination path; persisted commit drafts and workspace configuration are preserved. Read-only volumes and App Translocation use a manual-install explanation. Ad-hoc/EdDSA signing does not confer Developer ID trust or notarization.

HistoryQuery executes bounded native Git log queries; per-query generations discard stale results. Stash reads use immutable commit objects, including the third parent for untracked files, and reuse DiffTable without modifying Index. Remote edits distinguish raw configured URLs from effective fallback/rewrite URLs and preserve additional destinations. Multiple push URLs and inherited configuration require terminal editing rather than losing data.

Destructive local confirmations obtain a read-only GitOperationReview and recheck HEAD, branch, staged entries and merge/rebase operation identity inside the write queue. An external Index change since the visible snapshot requires refresh before confirming. ForcePushReview freezes a single effective push destination, reviewed local commit and exact remote-tracking lease; a later fetch cannot weaken the lease. ## Professional workflows (v1.2.0)

`ProfessionalWorkflow.swift` contains Sendable Reflog/Worktree/comparison/Blame models and NUL/porcelain parsers. All Git commands remain in `GitService.swift`. `ReflogView`, `WorktreesView`, `BranchComparisonView` and `BlameView` use existing navigation, CommitDetailView, DiffTable, code fonts, SyntaxHighlighter and scrollbars. `WorkflowRequest` cancels superseded tasks and rejects late results with generation tickets.

Reflog uses native `log -g` filtering/pagination (100 per UI page, at most 500 per service query). Dates come from reflog selectors rather than commit author timestamps. Repeated records retain separate page identities. Recovery resolves a full immutable commit ID before creating a branch; it never checks out or discards files. Soft/mixed reset is separately reviewed against the existing HEAD/Index/operation snapshot. There is no automatic hard reset, reflog expiry or garbage collection. Missing objects cannot be recovered from a log entry alone.

Worktree lifecycle operations hold the canonical-working-tree write queue and an additional FIFO keyed by normalized Git Common Directory, so sibling actors cannot concurrently change shared lifecycle metadata. Paths from Git and Foundation are normalized consistently, including macOS `/var` and `/private/var` aliases. `WorkspaceConfiguration.ownedWorktrees` persists creation receipts (path, common directory, linked git directory and creation UUID); absent fields in older configurations decode to an empty list. A mode-0600 `gitpier-creation-id` marker inside the native linked metadata directory binds the receipt to that creation, so an externally replaced tree cannot inherit removal permission from a reused path/metadata name. Only GitPier-created directories with matching receipts and markers can be removed. The service revalidates registration, HEAD/branch, path, lock, operation and modified/untracked/ignored files before invoking native `worktree remove` without force. Main, missing, prunable and unknown directories remain intact. Detached commits require a retaining branch/tracking ref/tag before removal. The UI protects drafts and active terminals, shows the affected path, then removes only corresponding workspace records. Repair verifies the moved linked tree's pointer belongs to the common directory and its original location is missing; it changes metadata without moving files. Existing organization, IDs and per-tree models remain independent.

Comparison resolves full local/remote-tracking refs to fixed hashes before `merge-base --all`, `rev-list --left-right --count`, paged unique `log` queries and file-level Diff. Direct mode uses A → B; three-point mode uses the unique merge base → B. Unrelated histories can use direct mode; ambiguous/missing merge bases reject three-point mode explicitly. No checkout, fetch, merge or rebase runs. Blame uses `--line-porcelain --no-textconv -M -L`, preserves Git's original path attribution after renames, distinguishes zero-hash working lines and links available commits to shared details. UTF-8 text is limited to 4 MiB and queried 400 lines per page (maximum 1000). Binary, oversized and unsafe/symlink files are refused; the Blame UI also refuses single lines over 20,000 characters to protect native text layout. Historical pages pin the resolved commit; working-file pages intentionally read the current disk version.

An explicitly selected GitPier HTTPS Token remains exclusive: native Askpass must not substitute another account when that Token cannot be read. A server-challenged negative regression verifies this with a valid original Askpass provider and an unavailable selected Token.

## v1.5.1 hosting boundary

`HostingModels` defines canonical HTTPS instances, capability differences, stable provider/instance/user identities, public OAuth configuration, tokens and repository bindings. `HostingHTTPClient` constructs only instance-owned routes; its ephemeral URLSession transport blocks redirects, retains system TLS trust and bounds streamed data. Provider DTO normalization, reconstructed pagination, exact-SHA CI, read-only review data and confirmed creation live in `HostingAPIClient`; no hosting API calls go through GitService.

`OAuthAuthorizationCoordinator` separates GitHub Device Flow from PKCE exchange/refresh. `OAuthPKCESession` owns secure state/verifier/S256, callback origin/path/expiry and consumption. `HostingBrowserSession` opens the ordinary default browser through an injectable `NSWorkspace` opener. AppDelegate receives the registered private-scheme URL and forwards it to `OAuthBrowserCallback`, which accepts one matching callback, buffers an early callback, enforces the deadline/cancellation and ignores malformed/foreign/stale URLs. The application restores its original window after validation. No ASWebAuthenticationSession or browser automation permission is used. GitHub opens its validated Device Flow verification URL once when the code arrives; the external opener is injectable for native fixtures. `OAuthLoopbackListener` owns a one-session, size/time-limited 127.0.0.1 listener. `OAuthTokenManager` shares lazy local / explicitly unlocked Keychain sessions across windows, merges loads and refresh tasks, and guards rotation against late reconnect/disconnect results. `HostingCredentialRouter` selects each account’s actual mode. `LocalEncryptedCredentialStore` protects the complete pair with CryptoKit AES-256-GCM and an atomic version pointer; `HostingKeychainStore` retains the existing account-bound service. Migration holds the per-account persistence section through a durable intent and atomic metadata commit; explicit cleanup follows. Disconnection tombstones move accounts out of the active account list before independent credential cleanup; outstanding storage modes remain visible for explicit retry and never participate in session restoration. See [credential storage](credential-storage.md).

`HostingModel` bridges metadata, authorization and account states to SwiftUI. Hosting metadata lives beside the workspace, not in its existing schema. Corruption disables saves and preserves the original. Settings, binding, request/detail/read-only Diff and creation views use independent requests/cancellation generations. Request rows do not prefetch review or CI pages. `HostingRequestDetailLoader` renders the supplied Overview immediately and uses independent cancellable module/page requests; its account-partitioned, revision-keyed memory cache merges readers and cancels the HTTP flight when the last reader leaves. Overview refresh can invalidate stale module generations without blocking the page. Reviews, inline comments and ordinary GitHub conversations have separate paging and errors. CI permissions remain errors, with No Checks reserved for successfully exhausted pages. Dashboard status reads use a separate two-permit network budget; they never consume Git's local operation budget or initiate Fetch. Descriptions/comments use selectable plain text. Creation reviews fix account, repository, source/target SHA and form input, recheck duplicate/fork/pushed/local state and require confirmation before the sole POST.

The existing GitService actor/FIFO/Common Directory queues, partial Index preservation, helpers/SSH/Askpass and Automatic Fetch scheduler are unchanged. The maintainer-registered public OAuth IDs are centralized in `HostingOAuthConfiguration.json`; no backend or secrets are bundled. Native fixture acceptance uses explicit disposable-workspace entry points and injected synthetic providers. A separate owner-operated `hosting-live` scope uses real provider HTTP and manual browser approval only through the explicit `--ui-acceptance` entry point. It requires an isolated test Bundle ID and run-specific workspace, Local Vault and Keychain service; checkpoints contain public metadata, booleans and opaque identifiers, with no Token, Refresh Token or encryption-key values. Neither acceptance path changes normal startup or provides a production fallback. See [OAuth setup](oauth-setup.md) and [validation](development.md#v151-hosting-stability-validation) for real-platform results and remaining checks.

Unified Diff parsing validates ASCII ranges, representable coordinates and both declared body counts. Invalid input retains its raw text but yields no actionable hunks/line pairs. CRLF control lines and content bytes remain preserved. Remote review uses the raw read-only fallback for such input; it cannot stage, apply or discard changes.
