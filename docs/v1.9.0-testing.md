## Delivered architecture

- History multi-selection and ordered Cherry-pick review reuse CommitDetailView/Diff, AppAppearance and shared overlay scrollbars. The native Git sequencer owns execution and recovery, bounded to 200 reviewed full IDs. Merge Cherry-pick is explicitly unsupported; duplicate/empty outcomes stop rather than being auto-skipped.
- Ordinary and merge Revert use the same typed review and original bounded PendingAction, with explicit parent selection for merges and a Diff entry. The older MergeRevert API remains a compatibility facade over the same executor.
- Repository-owned confirmed writes outlive sheet/page dismissal. Read tickets reject stale selection/page/executable results. Recovery revalidates repository filesystem identity, HEAD/branch/Index, native metadata and changed-file fingerprints, with native hooks/signing left enabled.
- Branch Health uses a bounded batch of local/tracking refs, native merged query and worktree registrations. The target reference/hash is explicit; no implicit Fetch, cleanup or deletion recommendation. Dashboard/context reuse existing local facts and provenance rather than starting another scan system.

## Reproducible performance

`RepositoryPerformanceTests.testGraphDeterministicWideHistory` constructs 8,192 immutable synthetic commits with 64 parallel lanes and measures five complete layouts in Debug. Baseline on this machine: **915.024, 926.028, 935.267, 930.335, 941.016 ms** (median **930.335 ms**), in `boundary-and-baseline.log`. A separate hand-derived merge geometry fixture protects edge positions, directions and colors. These are algorithm measurements, not a claim about end-user scrolling latency.

`testLargeBranchInventoryAndPagedHistory` generates 1,026 local refs in an isolated repository via one native update-ref input, checks explicit merged membership and bounded history paging, and records five health scans. Initial scan samples: **304.793, 306.510, 298.345, 314.765, 324.675 ms**. No per-branch Git process is launched; opt-in process tracing is required for launch counts (disabled counters read zero). After optimization (`performance-after.log`), layout samples are **305.579, 304.569, 307.277, 302.928, 299.082 ms** (median **304.569 ms**): approximately **3.05×** the baseline throughput / **67.3%** less layout time. Edge geometry and wide-lane completion assertions pass. Health samples are **306.449, 297.248, 341.374, 315.746, 297.328 ms**; opt-in tracing reports **95 launches for five scans (19 per scan)**, independent of the 1,026-ref count. These values describe this fixture/environment, not a universal UI speedup.

Existing protections remain: History queries cap each page at 500 (UI uses 100), graph work runs off the main actor, Diff caches remain 64 entries / 32 MiB, Index statistics omit binary payloads, conflict text remains bounded, and Dashboard keeps the original scan concurrency/budget. No Index, draft, file selection or terminal state is changed by scrolling or health analysis.

## Supported review limits

Commit replay accepts 1–200 distinct full IDs; Revert remains single-commit. Merge Cherry-pick is unsupported, and Merge Revert supports up to 64 explicitly ordered parents. Commit metadata reads cap each object at 1 MiB and the review at 8 MiB; native operation metadata has per-file/total bounds, preserving the existing 16 MiB saved Rebase-message allowance. Root `.git` pointers are read without following file links and capped at 64 KiB. Unsupported/corrupt metadata remains available for explicit terminal recovery; no data is cleared automatically.

## Independent review and corrected boundaries

One user-authorized read-only subagent reviewed the Git mutation/recovery changes. It did not write files, build, run tests or use GUI. Four initial regression tests reproduced **11 failing assertions** in `review-red.log`: a new replace mapping applied an unexpected file at the same source full ID; changed graft/shallow ancestry escaped the old review; Continue committed an externally substituted Index blob during the second final status; a valid custom fetch namespace was reported missing. A further final-gate ordering regression failed two assertions in `review-final-order-red.log`; its fix keeps all asynchronous object-view reads before the final clean-state check. The intermediate 51-test focused run passed in `review-fixed-core.log`; the subsequent full Core run (`core-reviewed.xml`) passed 1050 tests with zero failures/errors/skips. Production code matched the reviewed freeze; only additional native-acceptance diagnostics changed afterward.

Replay tickets now bind the effective replace-ref map (including tree/blob replacements), relevant effective Git configuration/environment, and bounded bytes of both default and actual custom graft/shallow files. Unsupported replacement namespace shapes are explicitly refused; supported namespaces must start with `refs/` and end with `/`. Native Git semantics are retained. Metadata is captured between matching object views; shared Diff validates before loading and before publishing; Revert uses the newly reviewed record and parent order rather than cached History metadata.

Recovery fingerprints parse one complete raw porcelain snapshot including HEAD/branch and staged object IDs, hash changed working files, then require an identical second raw snapshot and the expected HEAD/branch. Synchronous filesystem/operation/overlay checks follow. Recovery confirmation displays its fixed operation, current full ID and complete todo; a changed displayed sequence must be reviewed again. These are optimistic external-client checks followed by native Git's own locks and conflict checks, not a cross-process transaction or a lock on every external Git client.

Health uses Git's native `[gone]` tracking marker, so custom fetch destinations outside `refs/remotes/` remain valid upstreams. Published badges must match every displayed local branch hash/current/upstream/tracking fact and the displayed HEAD/branch/operation; mismatches require repository Refresh. Matching uses a reference dictionary after uniqueness checks. Fetch history is shown only when the complete current `WorkspaceFetchTarget.id` (including configuration/refspec identity) matches the cached workspace source, explicitly labeled for the current remote; otherwise Unknown.

The enhanced native run first timed out while checking recovery text (`ui-review-fixed.log`). The acceptance harness now waits for the recovery button to become enabled and checks both accessibility label and value against the localized message; `ui-reviewed` passed without changing product code. System-composited `replay-visible-light.png` / `replay-visible-dark.png` were inspected for actual native appearance. AppKit bitmap captures can omit native materials/glyphs; they are not used alone to judge appearance.

## Final native Release performance observations

`native-performance-reviewed/performance.json` records the final production source with 10,001 tracked files / 1,001 changed files, 1,000 history commits, 10 repositories (including linked Worktree switching) and 100,000 terminal lines. The app's reported peak RSS was **295.625 MiB**; repository refresh median **202.828 ms** over five samples, and the ten-repository native switch workload median **412.071 ms** over three samples. These are end-to-end observations, not per-repository guarantees or a proof of leak-free behavior.

Main-loop sampling still observed first/update peaks: **101.609 ms** for the 1,000-commit History update and **215.752 ms** during repository switching. These remain profiling targets before a broad smoothness claim; this task claims the separately measured graph-layout improvement only. The earlier native run is retained in `native-performance/`; it is not a pre-feature baseline for claiming a whole-application speedup. Native and Debug algorithm timings are not combined into one comparison.
